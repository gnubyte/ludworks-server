# API overview

Everything in Ludworks — the web UI, the apps, the browser extension, the Python SDK — uses one HTTP API.
You can use it too: for scripts, home automation, backups or AI agents.

* **Base path:** `/api/v1` on your server, e.g. `https://nas.local:8443/api/v1/health`.
* **Interactive reference:** every server serves **Swagger UI at `/api/docs`** and the machine-readable
  **OpenAPI 3.1** document at `/api/openapi.json`. Swagger UI lets you try requests with your session or a
  token. A token entered under *Authorize* is kept only in memory and forgotten when the page is reloaded or
  closed; prefer a narrowly scoped, short-lived personal access token there.
* **Static reference:** the [endpoint reference](reference.md) lists every operation with its scope.
* **Contract:** the normative specification is the [HTTP API contract](../spec/API.md).

## Conventions

* JSON in UTF-8 with `snake_case` fields. Request bodies are limited to 1 MiB unless an endpoint says otherwise
  (uploads and imports take raw bodies with their own limits).
* IDs are opaque strings (`^[A-Za-z0-9_-]{8,64}$`; server-generated IDs are 26-character base32). Vault item and
  folder IDs are UUIDs generated by the client.
* Timestamps are RFC 3339 in UTC with milliseconds: `2026-10-26T12:00:00.123Z`. Durations are seconds
  (fractions allowed).
* JSON bodies must be sent with `Content-Type: application/json` (otherwise `415`). Unknown fields are
  **ignored** for forward compatibility — so double-check field names; a typo is silently dropped.
* Boolean query parameters are true for `1`, `true`, `yes` or `on` (case-insensitive) and false otherwise.

## Authentication in one paragraph

Browsers use the `lw_session` cookie plus an `X-CSRF-Token` header on unsafe requests. Programs use
`Authorization: Bearer <token>` with either a session token from `POST /api/v1/auth/login` with
`"token_mode": true` (full access of the user) or a **personal access token** limited to scopes. Streaming URLs
for media players may carry the token as `?access_token=`. Details: [Authentication](authentication.md).

```bash
TOKEN=$(curl -s https://nas.local:8443/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"alice","password":"…","token_mode":true,"device_name":"my-script"}' | jq -r .token)
curl -s -H "Authorization: Bearer $TOKEN" https://nas.local:8443/api/v1/me
```

(Add `--cacert` with your server certificate, or `--pinnedpubkey`, when using the self-signed certificate; the
examples omit it for brevity.)

## Errors

Errors use the HTTP status code and a JSON body:

```json
{ "error": { "code": "validation_failed", "message": "validation failed", "details": { "fields": { "name": "must not be empty" } } } }
```

| Status | Codes | Meaning |
|---|---|---|
| 400 | `bad_request` | Malformed JSON, missing body, data after the JSON value, invalid parameter |
| 401 | `unauthorized`, `invalid_credentials`, `totp_required` | Not logged in / token invalid or expired; wrong password; second factor needed |
| 403 | `forbidden`, `registration_disabled` | Missing scope or role, disabled account, missing CSRF token |
| 404 | `not_found` | Does not exist **or you may not see it** |
| 409 | `conflict` | Name taken, stale version (`details.current` holds the server copy for notes and vault items) |
| 410 | `gone` | Expired upload or token; a sync position (`since`, cursor) that is no longer valid — do a full sync |
| 413 | `payload_too_large` | Body over the endpoint's limit |
| 415 | `unsupported_media_type` | JSON endpoint called without `application/json`, or an unsupported file format |
| 422 | `validation_failed` | Field errors in `details.fields` |
| 429 | `rate_limited` | Slow down; wait `Retry-After` seconds |
| 500 | `internal` | Server bug (details are logged server-side, never returned) |
| 501 | `not_implemented`, `ffmpeg_unavailable` | Optional feature not available on this server |
| 503 | `setup_required` | The server has not been set up yet |
| 507 | `quota_exceeded`, `insufficient_storage` | Your quota is full / the disk is full |

Some endpoints add specific codes, such as `smtp_failed` / `imap_failed` (502) for mail tests and status `460`
for a tus chunk checksum mismatch. Always branch on `error.code`, not on the message text.

## Pagination

Lists that can grow large are cursor-paginated: pass `limit` (default 50, max 200) and receive

```json
{ "items": [ … ], "next_cursor": "eyJrIjoi…" }
```

Request the next page with `?cursor=<next_cursor>` (and the same filters) until `next_cursor` is `null`.
Cursors are opaque and signed; do not build or modify them. Small, bounded lists (spaces, channels, folders,
tags) are returned as plain arrays.

## Rate limits

* Login, 2FA, password reset and setup: per IP and per account; 5 failures free, then exponential lockout up
  to 15 minutes. Attempts still in progress count as failures, so sending many at once gains nothing.
* Everything else, signed in: 200 requests/second per user, bursts up to 1000.
* Everything else, not signed in: 30 requests/second per client IP, bursts up to 120.
* Not counted against those limits (they are bounded by their own per-upload locks and concurrency caps):
  tus upload chunks and offset queries (`PATCH`/`HEAD /api/v1/uploads/{id}`) and `Range` requests for file,
  media and recorded-program content (`GET /api/v1/files/{id}/content`, `GET /api/v1/media/{id}/stream`,
  `GET /api/v1/tv/channels/{id}/programs/{file_id}/stream`).

A `429` response carries `Retry-After` (seconds). Well-behaved clients back off and retry; the Python SDK does
this automatically.

## Concurrency control

Notes (`base_version`), vault items and folders (`base_revision`) use optimistic concurrency: send the version
you edited; if someone changed the record in the meantime you get `409 conflict` with the current server copy
in `details.current` to merge. Browser sync writes many records at once, so it reports a conflict per record
(`status: "conflict"` with `current`) in a `200` response instead.
