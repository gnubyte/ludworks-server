# Ludworks Vault — End-to-End Encryption Spec (v1)

The password vault is zero-knowledge: the server stores only ciphertext and KDF parameters. Every client
(web UI, browser extension, Android `:vault`, desktop `Ludworks.Desktop`, Python SDK `[vault]`) implements
exactly this spec. Primitives were chosen to be available natively everywhere (WebCrypto, .NET,
javax.crypto, Python `hashlib` + `cryptography`).

## 1. Keys

```
password_bytes = UTF-8( NFC-normalize(master_password) )
master_key     = PBKDF2-HMAC-SHA256(password_bytes, kdf_salt, kdf_iterations, dkLen = 32)
wrap_key       = HKDF-SHA256(IKM = master_key, salt = <empty>, info = "ludworks/vault/wrap/v1", L = 32)
vault_key      = 32 random bytes (CSPRNG), generated at vault init and at every key rotation (§2.3)
wrapped_key    = Seal(wrap_key, vault_key, AAD = "ludworks/vault/key/v1")
key_check      = Seal(vault_key, "" (empty plaintext), AAD = "ludworks/vault/check/v1")
key_id         = random UUID assigned by the server; names the current vault_key (§2.2)
```
* `kdf_salt`: 16 random bytes, standard base64 (with padding) on the wire.
* `kdf_iterations`: default **600000**; server rejects < 600000; clients must accept up to 10,000,000.
* HKDF with empty salt = RFC 5869 with salt = 32 zero bytes. (WebCrypto: `salt: new Uint8Array(0)`.)
* The master password is never sent to the server. It is separate from the account login password.
* `key_check` is a commitment to the vault key (its ciphertext is exactly the 16-byte GCM tag). Clients send it with
  `POST /vault/init` and `POST /vault/rekey`; vaults created before it existed have `key_check: null` until a client
  that unwrapped the key with the master password stores one (`PUT /vault/key-check`, set once).
* `key_id` is new at every init and every rotation and unchanged by a master-password change. It is not secret.

## 2. Sealed strings

```
Seal(key, plaintext, aad) = "v1." + b64(nonce) + "." + b64(ciphertext || tag)
    AES-256-GCM, nonce = 12 random bytes, tag = 16 bytes, aad = UTF-8 bytes of the AAD string.
Open(key, sealed, aad)    = parse, verify version "v1", AES-256-GCM decrypt; tag failure → error.
```
`b64` = standard base64 with padding (RFC 4648 §4). Unknown version prefix → error.

| Object | Plaintext | AAD |
|---|---|---|
| wrapped vault key | 32 raw key bytes | `ludworks/vault/key/v1` |
| key check | empty | `ludworks/vault/check/v1` |
| vault item `data` | UTF-8 JSON (§3) | `ludworks/vault/item/v1:<item id>` |
| vault folder `name` | UTF-8 JSON `{"name":"..."}` | `ludworks/vault/folder/v1:<folder id>` |

Binding the id into the AAD prevents a malicious server from swapping ciphertexts between records.
Item and folder ids are generated by the client (UUID v4, lowercase, with hyphens).

Unlock = derive `wrap_key`, `Open(wrapped_key)`. A tag failure means a wrong master password. The key unwrapped
with the master password is authoritative: a `key_check` that does not open under it is reported, not trusted.

### 2.1 Change master password
New salt → new `wrap_key` → re-`Seal` the same `vault_key` → `PUT /vault/key` with `previous_wrapped_key` (and
`key_id`). Items, `key_id` and `key_check` are untouched. `kdf_iterations` must be **max(current, 600000)** (or
higher if the user asks): a client must never silently lower a work factor chosen on another device, and the server
refuses a lower count (422 on `kdf_iterations`) unless the request sets `"allow_kdf_downgrade": true` because the
user explicitly asked for it. A password change does **not** lock out anyone who already holds an old `wrapped_key`
(backup, stolen device, earlier `GET /vault`) together with the old master password: they still unwrap the same
`vault_key`. That needs a key rotation (§2.3).

### 2.2 Key identity and freshness (normative)
A client may hold a vault key that it did not just unwrap from the current `wrapped_key`: an unlocked session that
stays open (web tab, extension session), the desktop DPAPI copy, the Android Keystore/biometric copy, an SDK cache.
After a vault reset + re-init or a key rotation on another device that key is retired, and anything sealed under it
is unreadable for every other device. Therefore:
* Clients remember the `key_id` their key belongs to. Every record write names it — body field `key_id` on JSON
  writes (`POST/PUT /vault/items…`, `POST /vault/items/batch`, `POST/PUT /vault/folders…`, `PUT /vault/key`), query
  parameter `?key_id=` on `DELETE`. The server answers **409 `vault_key_changed`** when it is not the current
  `key_id` (or when no vault exists any more); the client must then forget the key and lock. Writes without
  `key_id` are still accepted for older clients; current clients must always send it.
* `GET /vault/sync` returns the `key_id` its records are sealed under (`null` without a vault). A client whose key has
  another `key_id` must not merge the records: it locks (and re-reads `GET /vault`).
* Before using a remembered key (and at least on every app start, resume/visibility change and after a sync `410`)
  clients re-read `GET /vault` and lock/forget the key when `key_id` differs. A remembered copy that is reused
  without the master password must additionally `Open(key_check)` successfully (when `key_check` is not null);
  on failure the copy is deleted and the master password is required. A changed `wrapped_key` with the same
  `key_id` means the master password was changed elsewhere; the web UI locks then too.
* After unlocking with the master password, a client that sees `key_check: null` stores
  `Seal(vault_key, "", "ludworks/vault/check/v1")` with `PUT /vault/key-check {key_id, key_check}` (best effort).

### 2.3 Rotate the vault key
Recommended whenever the master password, a device or a server backup may have been compromised (the web UI offers
it together with a password change and on its own). The client:
1. verifies the current master password (unwraps the current `wrapped_key`) and does a full sync; it refuses to
   rotate while any live record cannot be decrypted (it could not be re-sealed and would be lost);
2. generates a new random `vault_key`, a new salt and `wrapped_key` under the new (or unchanged) master password with
   `kdf_iterations` = max(current, 600000), and the new `key_check`;
3. re-seals every live item (same id/AAD, `seq` + 1, §2.5) and every live folder under the new key;
4. sends `POST /vault/rekey {kdf, kdf_iterations, kdf_salt, wrapped_key, key_check, previous_wrapped_key, key_id,
   items:[{id, base_revision, data}], folders:[{id, base_revision, name}]}`.

The server commits everything in one transaction or nothing: `previous_wrapped_key` and `key_id` must be current, and
the submitted ids must be exactly the live items and folders at exactly those revisions (else 409; nothing changes,
the client syncs and retries). On success every record's revision is bumped, the vault gets a new `key_id` (writes
naming the old one now get 409 `vault_key_changed`) and a new sync horizon (every device's next delta sync gets 410,
does a full resync and notices the new key). The response is the new `GET /vault` state. Request bodies are limited
to 64 MiB; larger vaults rotate by export → reset → import. Afterwards the old `wrapped_key` + old password, and every
remembered copy of the old key, open nothing that is stored now or later (ciphertext copied before the rotation
stays readable to whoever holds the old key — rotate the stored passwords themselves after a compromise).

### 2.4 Client obligations after a key change
Clients that remember a key (DPAPI, Keystore, extension `vaultMeta`/cache, SDK) store its `key_id` (and may check
`key_check`) and delete the remembered copy and any cached ciphertext of the old key when §2.2 detects a change,
instead of waiting until every item fails to decrypt.

### 2.5 Item freshness and rollback (limits)
AES-GCM with the record id in the AAD stops ciphertexts being swapped between records, but every older ciphertext of
the *same* record still authenticates, and `folder_id` is server-side metadata. To let clients detect a server (or
anyone with write access to its database or backups) replaying an older version, the item plaintext carries:
* `seq` — integer edit counter: a new item starts at 1; every client write of an existing item sets
  `seq = max(previous plaintext seq, 0) + 1` (missing = 0). It is authenticated (inside the ciphertext); do not use the
  server `revision` for this (the server bumps revisions without re-encrypting, e.g. when a folder is deleted).
* `folder_id` — the folder the writer filed the item in (`null` = none). Moving an item re-seals it. Readers ignore a
  plaintext `folder_id` that names a folder that is no longer live (the server un-files items when a folder is
  deleted); otherwise a mismatch with the record's `folder_id` means the record was moved without re-encryption.

Clients with persistent state (extension cache, Android cache, desktop, SDK caches) keep, separately from their sync
cache and per vault `key_id`, a high-water mark per item `{seq, updated_at}` and the ids they saw deleted, kept across
`410` full resyncs; they must keep the newer version (and warn) when a sync offers a lower `seq`, the same `seq` with
different ciphertext, or a re-appearing deleted id, and never use such a record for autofill. Remaining limits, by
design: the server can withhold records or changes, and can serve old versions to a client that has never seen the
newer ones; the web UI is served by the server itself, so a malicious server can attack it directly (rollback checks
protect the clients that do not load code from the server). A sealed vault-wide manifest (`{id: seq}` map with a vault
counter) would close the withholding gap and is not part of v1.

## 3. Item plaintext schema (JSON)

```json
{
  "type": "login" | "note" | "card" | "identity",
  "name": "GitHub",
  "favorite": false,
  "notes": "free text",
  "login": {
    "username": "me@example.com",
    "password": "…",
    "uris": [ { "uri": "https://github.com/login", "match": "domain" } ],
    "totp": "otpauth://totp/GitHub:me?secret=JBSWY3DPEHPK3PXP&issuer=GitHub"
  },
  "card":     { "cardholder": "", "brand": "", "number": "", "exp_month": "", "exp_year": "", "code": "" },
  "identity": { "title": "", "first_name": "", "middle_name": "", "last_name": "", "company": "",
                "email": "", "phone": "", "address1": "", "address2": "", "city": "", "state": "",
                "postal_code": "", "country": "", "username": "", "ssn": "", "passport": "", "license": "" },
  "fields": [ { "name": "PIN", "value": "1234", "hidden": true } ],
  "password_history": [ { "password": "old", "changed_at": "2026-01-01T00:00:00Z" } ],
  "created_at": "2026-10-26T12:00:00Z",
  "updated_at": "2026-10-26T12:00:00Z",
  "seq": 3,
  "folder_id": "b2d4f6a8-1c3e-4f5a-8b7c-9d0e1f2a3b4c"
}
```
Only the sub-object matching `type` is required; unknown keys must be preserved on edit (forward
compatibility). `totp` may be a bare base32 secret or an `otpauth://` URI. `seq` and `folder_id` are the
authenticated freshness fields of §2.5 (writers maintain them; missing `seq` = 0); they are vault bookkeeping and are
not exported or taken from imported files.

URI `match` values: `domain` (default: same registrable domain, §3.1), `host` (exact host+port), `starts_with`,
`exact`, `regex`, `never`. IP addresses and `localhost` compare by host (and port, §8.3).

**Passkeys** (WebAuthn credentials, §10) live in login items as `login.passkeys`, so they sync, back up, import and
export with the login they belong to:

```json
"passkeys": [ {
  "credential_id": "<base64url, no padding: raw credential id bytes>",
  "rp_id": "example.com",
  "rp_name": "Example",
  "user_handle": "<base64url: user.id bytes>",
  "user_name": "me@example.com",
  "user_display_name": "Me",
  "algorithm": -7,
  "private_key": "<base64url: PKCS#8 DER of the P-256 private key>",
  "counter": 0,
  "discoverable": true,
  "created_at": "2026-10-27T12:00:00Z"
} ]
```
`algorithm` is a COSE algorithm identifier; only `-7` (ES256, P-256) is created or used by Ludworks clients, other
entries are kept but never offered. `counter` 0 means the credential does not use a signature counter (synced
passkeys normally do not). Clients that do not implement passkeys preserve the array like any unknown key; editors
show passkeys read-only (delete only). A passkey's `private_key` is a secret on par with `login.password`.

### 3.1 Registrable domain (Public Suffix List)
Registrable domain = the public suffix of the host plus one more label (eTLD+1), where the public suffix is computed
with the **Public Suffix List including its PRIVATE section** (so `github.io`, `duckdns.org`, `synology.me`, `ts.net`,
`herokuapp.com`, `pages.dev`, `s3.amazonaws.com`, `me.uk`, `ne.jp`, `gob.mx` … are suffixes and their tenants are
different sites). Algorithm (publicsuffix.org): hosts are lowercased, converted to ASCII (IDNA/punycode) and stripped of
a trailing dot; the matching rule with the most labels wins, an exception rule (`!www.ck`) always wins and removes its
leftmost label, wildcard rules (`*.ck`) match exactly one extra label, and no match means the implicit rule `*`.
A host that is itself a public suffix (e.g. an item URI `https://github.io`) is its own registrable domain, so it only
ever matches that exact host. IP addresses, `localhost` and single-label hosts are returned unchanged.

Every client embeds the **same pinned snapshot** and never downloads the list at runtime: the normative copy is
`web/assets/js/lib/vault/psl-data.js` (one rule per line, ICANN + PRIVATE, ASCII, `*.`/`!` prefixes kept), generated by
`node web/tests/vault/gen-psl.mjs <public_suffix_list.dat> <date> --write` from the publicsuffix.org list of
**2026-01-29** (`public_suffix_list.dat` sha256 `f3604fee29f4a2234547ca068da1e4c6a1c480418f1c418d4b4040633be501b4`,
6930 ICANN + 3189 private rules). Clients copy that rule list (or generate it from the same file with the same
normalisation) and must pass the `registrable_domain` and `url_match` vectors (§8.1). Refresh the snapshot in all
clients together and regenerate the vectors.

## 4. TOTP
RFC 6238: default SHA-1, 6 digits, 30 s period; honour `algorithm=SHA1|SHA256|SHA512`, `digits=6|7|8`,
`period` from `otpauth://` URIs. Base32 secrets are case-insensitive, spaces/padding ignored.

## 5. Password generator
CSPRNG with rejection sampling (no modulo bias). Options: length 8–128 (default 20), sets
upper/lower/digits/symbols (`!@#$%^&*()-_=+[]{};:,.?/`), exclude ambiguous (`Il1O0`), at least one from each
enabled set. Passphrase mode: 3–12 words from a bundled ≥ 2048-word list (EFF short list style), separator,
capitalize, include number.

## 6. Import / export (client-side only)
* **Bitwarden**: unencrypted JSON export (`folders[]`, `items[]` with `type` 1 login, 2 secure note,
  3 card, 4 identity, `fields[]`, `login.uris[]`, `login.totp`, `login.fido2Credentials[]` (passkeys, §8.4),
  `passwordHistory`) and CSV
  (`folder,favorite,type,name,notes,fields,reprompt,login_uri,login_username,login_password,login_totp`).
  Password-protected Bitwarden JSON (`"encrypted": true, "passwordProtected": true`) import is supported:
  PBKDF2-SHA256 or Argon2id per its `kdfType`, then Bitwarden's EncString type 2 (AES-CBC-256 + HMAC-SHA256).
* **KeePass 2**: KDBX 4.0/4.1 read+write (outer cipher AES-256-CBC or ChaCha20; KDF AES-KDF or
  Argon2d/Argon2id; HMAC block stream; inner stream ChaCha20 (id 3) or Salsa20 (id 2); gzip),
  KDBX 3.1 read (AES-KDF, hashed block stream, Salsa20 inner stream), and KeePass 2 XML read+write.
  Export writes KDBX 4.0, AES-256-CBC, Argon2d (memory 64 MiB, iterations 2, parallelism 2 — KeePass
  defaults are acceptable), ChaCha20 inner stream, gzip. Groups ↔ folders (nested paths joined with `/`),
  entries' `Title/UserName/Password/URL/Notes` + custom strings → fields, `otp` / `TimeOtp-Secret-Base32`
  → totp, History → password_history. Optional key file (KeePass XML key file v1/v2, or raw 32-byte / 64-hex
  / hashed arbitrary file) supported for import and export.
* Export always warns that the output contains plaintext secrets (except KDBX, which is encrypted).

## 7. Client storage rules
* Never persist `master_key`, `wrap_key` or `vault_key` to disk unencrypted. Browser extension keeps
  `vault_key` only in `chrome.storage.session` (memory) and locks after the configured idle timeout
  (default 15 min) or browser restart. Android may keep a Keystore-wrapped copy of `vault_key` for
  biometric unlock (key requires user authentication). Desktop may keep a DPAPI-protected copy only if
  the user enables "remember on this device".
* Every remembered or long-lived key is stored with its `key_id` and is re-validated per §2.2 (current `key_id`,
  `key_check` opens) before use; on mismatch the copy and the cached ciphertext are deleted (§2.4).
* Re-wrapping keeps the vault's work factor (§2.1); rotation is the only way to retire a vault key (§2.3).
* The local encrypted cache (sync payload) may be persisted for offline read access. Clients that persist it keep
  the per-item high-water marks of §2.5.

reproduce the TOTP codes. Regenerate with `node web/tests/vault/gen-vectors.mjs --write` (this also rewrites the

### 8.2 Generator determinism (normative only for reproducing the vectors)
* Byte stream: `SHA-256(seed ‖ LE32(0)) ‖ SHA-256(seed ‖ LE32(1)) ‖ …`, seed = UTF-8 `ludworks/vault/generator/v1`.
  Each draw consumes the next 4 bytes as a little-endian uint32 `x`. Production uses the platform CSPRNG instead.
* `randomInt(n)`: `limit = 2^32 − (2^32 mod n)`; draw until `x < limit`; return `x mod n`.
* Password: enabled sets concatenated in the order upper, lower, digits, symbols (`Il1O0` removed from the first
  three when "exclude ambiguous" is on); draw `length` characters `pool[randomInt(|pool|)]`; if any enabled set is
  missing, discard the whole password and draw again (uniform over valid passwords).
* Passphrase: one `randomInt(N)` index per word into `web/assets/js/lib/vault/wordlist.js` (sorted, 3018 words);
  capitalise if requested; if "include number": `pos = randomInt(words)`, `digit = randomInt(10)`, append the digit
  to word `pos`; join with the separator. Defaults: 6 words, `-`, no capitalisation, no number.

### 8.3 Reference-implementation rules (all clients should match)
* **Unlock hardening:** clients refuse `kdf ≠ pbkdf2-sha256`, `kdf_iterations ∉ [600000, 10000000]` and salts that
  are not 16–64 bytes *before* deriving keys, so a malicious server cannot downgrade the KDF that a later re-wrap
  would reuse. Item/folder ids must match `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`.
* **URI matching:** `domain`/`host` only match `http:`/`https:` pages, and an `https` item URI never matches an
  `http` page (no autofill into a downgraded connection). Item URIs without a scheme get `https://`. `domain` compares
  registrable domains per §3.1 (PSL incl. private section). In `domain` mode, IP addresses, `localhost` and
  single-label hosts compare host **and port**. `host` compares host+port with default ports elided. `exact` compares
  raw strings. `starts_with` is a raw string prefix and, when the item URI is an absolute `http(s)://` URL, the page
  must also have the same origin (so `https://bank.com` never matches `https://bank.com.evil.net/`,
  `https://bank.com@evil.net/` or `https://bank.com:8443/`). `regex` is case-insensitive, ≤ 1000 chars, invalid
  patterns and patterns with a quantified group containing a quantifier (`(a+)+`, ReDoS shapes — vault data can come
  from imported files) never match. Unknown modes never match. Page URLs (and, in `domain`/`host` mode, item URIs)
  longer than 4096 characters never match.
  Clients that save logins automatically (autofill capture) should save them with `host` match (defence in depth),
  and should show the saved host when a fill relies only on registrable-domain equality.
* **TOTP:** HOTP is not supported; `steam://SECRET` (or `encoder=steam`) yields 5-character Steam Guard codes.

### 8.4 Import / export conventions (client-side, §6)
Interchange shape used by the import/export code: `{folders:[{id, name}], items:[{folderPath, ...§3 item}], warnings}`
where `name`/`folderPath` are full `/`-joined paths (segments trimmed, empty segments dropped; `''` = no folder).
* **KeePass ⇄ vault:** groups ⇄ folders (root group = database, not a folder; the recycle bin is skipped on import).
  `Title/UserName/Password/URL/Notes` map to `name/login.username/login.password/login.uris[0]/notes`; extra URIs ⇄
  `KP2A_URL`, `KP2A_URL_1`, … (KeePassXC convention); other strings ⇄ `fields` (Protected ⇄ `hidden`; duplicate or
  reserved names get a ` (2)` suffix on export). TOTP import recognises `otp` (otpauth URI, KeeOtp
  `key=…&size=…&step=…`, or bare base32), `TimeOtp-Secret[-Base32|-Hex|-Base64]` + `TimeOtp-Length/-Period/-Algorithm`,
  and KeePassXC's legacy `TOTP Seed` + `TOTP Settings`; export writes a protected `otp` field with an otpauth URI.
  KeePass has no favourites or item types: favourite ⇄ tag `Favorite`; other tags ⇄ item key `tags` (array);
  `note`/`card`/`identity` items carry entry CustomData `Ludworks.Type`, with card/identity values in strings named
  `Card Holder`, `Card Brand`, `Card Number`*, `Card Expiration Month`, `Card Expiration Year`, `Card Security Code`*,
  `Identity Title`, `First Name`, `Middle Name`, `Last Name`, `Company`, `Email`, `Phone`, `Address 1`, `Address 2`,
  `City`, `State`, `Postal Code`, `Country`, `Identity Username`, `SSN`*, `Passport`*, `License`* (* = protected).
  History: each password that differs from the next version becomes `{password, changed_at}` where `changed_at`
  is the next version's LastModificationTime (newest first); export writes one snapshot per old password.
  KeePass attachments are not imported (the item schema has none) and are reported in `warnings`.
* **KDBX:** the KeePass composite key uses the password's UTF-8 bytes **without** NFC normalisation (KeePass
  compatibility). Export writes KDBX 4.0 (4.1 only if the tree uses 4.1-only fields). Readers enforce limits on file
  size (1 GiB), decompressed data (512 MiB **in total**: the decompressed payload and every attachment decoded from
  `<Meta><Binaries>` share one budget; KeePass XML files get the same 512 MiB total), XML (256 Mi chars, depth 256),
  Argon2 memory (1 GiB) / iterations (100) / lanes (64) and AES-KDF rounds (2·10^8); larger files need an explicit
  opt-in. Importers that drop attachments (all vault imports) must not decode or decompress them at all — they only
  count them for the warning (and report attachments no entry links to). Errors distinguish
  `bad_credentials`, `bad_keyfile`, `corrupt`, `unsupported` (KeePass 1.x, Twofish, unknown KDF) and `limit_exceeded`.
* **Bitwarden:** JSON item types 1–4 map directly (`match` 0–5 ⇄ `domain, host, starts_with, exact, regex, never`;
  `null` = default); type 5 (SSH key) imports as a note with fields; linked fields, trashed items,
  organisation/collection ids and `reprompt` are not carried over (clients without passkey support also drop
  passkeys, with a warning). **Passkeys** `login.fido2Credentials[]` ⇄ `login.passkeys[]`: `credentialId` is a
  lowercase GUID string whose 16 raw bytes (RFC 4122 textual byte order) are the credential id, or `"b64."` +
  base64url bytes for any other id (export writes the GUID form for 16-byte ids, `b64.` otherwise); `keyValue`
  (base64url PKCS#8) ⇄ `private_key`; `rpId`, `rpName`, `userHandle` (base64url), `userName`, `userDisplayName` map
  directly; `counter` (decimal string) ⇄ integer; `discoverable` (`"true"`/`"false"`) ⇄ boolean; `creationDate` ⇄
  `created_at`; export writes `keyType: "public-key"`, `keyAlgorithm: "ECDSA"`, `keyCurve: "P-256"` and import skips
  (with a warning) entries with another type/algorithm/curve or a key that does not parse as P-256 PKCS#8.
  Password-protected export:
  `key = PBKDF2-SHA256(pw, UTF-8(salt string), N)` or `Argon2id(pw, SHA-256(UTF-8(salt string)), t, m MiB, p)`,
  `encKey/macKey = HKDF-Expand(key, "enc"/"mac", 32)`, EncString type 2 only (type 0 is refused);
  account-restricted encrypted exports cannot be decrypted outside Bitwarden. CSV columns per §6; `login_uri` is
  itself a comma-separated (CSV-quoted) list; `fields` holds `name: value` lines (split at the last `": "`); cards
  and identities, which Bitwarden CSV cannot express, are exported as notes with their values as fields.

## 9. Browser data (Ludworks Browser sync, API.md §16)

Bookmarks, history, open tabs and preferences are sealed with keys derived from the vault key, so the master
password protects them like vault items and a vault key change (§2.3) retires them together:

```
browser_key   = HKDF-SHA256(IKM = vault_key, salt = <empty>, info = "ludworks/browser/key/v1", L = 32)
browser_idkey = HKDF-SHA256(IKM = vault_key, salt = <empty>, info = "ludworks/browser/id/v1",  L = 32)
record data   = Seal(browser_key, UTF-8 JSON, AAD = "ludworks/browser/record/v1:<collection>:<id>")
derived id    = base64url-nopad( HMAC-SHA256(browser_idkey, UTF-8(<collection> + "\n" + <natural key>)) ), first 32 chars
```
Binding collection and id into the AAD stops a server from moving a record between collections or ids. Derived ids
let two devices name the same thing (a history URL) identically without telling the server what it is. Every record
plaintext carries `updated_at` (RFC 3339, client clock of the edit); a client keeps its local copy when the server
offers an older `updated_at` for a record it has already seen (rollback protection, cf. §2.5). Unknown keys are
preserved on edit.

| Collection | Record id | Plaintext |
|---|---|---|
| `bookmarks` | random UUID (client) | `{"type":"url"\|"folder","parent":"<id>","index":number,"title":str,"url"?:str,"created_at","updated_at"}` |
| `history` | derived id, natural key = the URL | `{"url":str,"title":str,"visits":[epoch ms, newest first, ≤ 30],"updated_at"}` |
| `tabs` | the device id (random UUID per installation) | `{"device":str,"platform":"windows"\|"macos"\|"linux"\|"android","tabs":[{"url","title","last_used":epoch ms}] (≤ 200),"updated_at"}` |
| `prefs` | `prefs` | `{"search_engine":str,"custom_search"?:{"name","url"},"homepage"?:str,"show_bookmarks_bar"?:bool,"updated_at"}` |

* **Bookmarks.** The three root folders are implicit and never stored: `toolbar` (bookmarks bar), `other` (other
  bookmarks) and `mobile`. `index` orders siblings ascending (ties by id); writers pick a value between the
  neighbours and renumber a folder's children 1, 2, 3, … when a gap falls below 1e-6. A node whose parent does not
  exist (or is deleted) is shown under `other`; a cycle is broken by moving the node that closes it to `other`.
  Deleting a folder deletes its descendants (each gets its own tombstone). Conflicts resolve per record, newest
  `updated_at` wins. URLs are stored as given (≤ 8 KiB); clients decide which schemes they open.
* **History.** Merging two copies of a record = union of `visits` (newest 30 kept), newest non-empty `title`.
  Clients keep at most 90 days and delete older records (with tombstones). Private-window browsing is never recorded.
* **Tabs.** Each device owns its record (only it writes it) and deletes it when it signs out.

## 10. Passkeys (WebAuthn authenticator in Ludworks clients)

Ludworks Browser acts as a WebAuthn authenticator whose credentials are the `login.passkeys` of §3 (synced,
"multi-device" credentials, like Bitwarden's). Normative rules for every client that implements it:

* **Algorithms and data.** ES256 only (`pubKeyCredParams` without `-7` → `NotSupportedError`, the caller may fall back
  to a platform/roaming authenticator). AAGUID `a70a1e9f-20e7-4d33-a38e-04115decb9c6`. Attestation format `none`
  (empty `attStmt`), whatever the RP asked for. Credential ids are 16 random bytes. Authenticator data flags: UP and UV
  set (the vault is unlocked with the master password and the user confirmed this very request in browser UI the page
  cannot draw over or script), BE and BS set (synced), AT on registration. `signCount` per §3: 0 stays 0; a non-zero
  counter is advanced to `max(counter + 1, unix seconds)` and written back before the assertion is returned.
* **Origin and RP ID.** The origin is the requesting frame's origin as the browser knows it (never anything the page
  says). Only secure contexts (`https:`, or `http:` on `localhost`) of top-level frames or frames same-origin with
  the top-level page may use the authenticator. `rp.id` (default: the origin's host) must equal the origin's host or
  be a parent domain of it whose registrable domain (§3.1, PSL incl. private section) equals the host's — a public
  suffix is never a valid RP ID; violations → `SecurityError`. IP-address hosts only accept themselves.
* **clientDataJSON** = `{"type":"webauthn.create"|"webauthn.get","challenge":<base64url>,"origin":<origin>,"crossOrigin":false}`
  serialised in exactly that member order (plus `"topOrigin"` after `crossOrigin` when it is true, which v1 never sends).
* **Registration.** `excludeCredentials` naming a stored passkey for the same RP → `InvalidStateError` (after the user
  confirms, per WebAuthn). The new passkey is added to a login item the user picks (default: an existing login for
  that site and user name, else a new login named after `rp.name`/RP ID with URI `https://<rp id>`, match `domain`,
  and `login.username = user.name`). Created passkeys are always discoverable.
* **Assertion.** `allowCredentials` (when non-empty) limits the candidates to those ids; otherwise every passkey for the
  RP ID is a candidate. The user picks one in browser UI. `userHandle` is returned for discoverable credentials.
  Conditional mediation (`mediation: "conditional"`) lists the candidates in the browser's autofill UI and resolves
  only when the user picks one.
* **Fallback.** The browser UI always offers "use another device or security key", which hands the unmodified request
  to the platform's own WebAuthn implementation.
